# Mission

A **mission** is one cross-session outcome with a destination. It ends when the destination is reached. It is bigger than one session and often bigger than one Jira epic. It can bundle Jira tickets, unlinked GitHub issues, harness work, ticket folders and sessions.

The skill fixes two failures that cost Gabriel weeks:
- **Lost thread.** He sees only the last screen of the terminal, so answers, blockers and decisions get buried. The fix is an HTML report on request, rendered from the record.
- **Stale context.** Session 3 writes a new file, session 1's file and the ticket stay stale, and session 4 reloads an idea that was already disproven. The worst case was the first run of a vendor integration: five security controls built on an unratified decision, then unwound. The fix is one record per mission. It holds decisions with authority, disproven claims, scope constraints and parked tracks, and every session reads it first and writes it back.

## Where things live

```
project-management/missions/
  INDEX.md                      generated list of all missions
  _meta/skill-usage.jsonl       usage and feedback log (self-improvement)
  _meta/closeout-log.jsonl      one line per close-out: buckets, big misses, human-found misses, checks fired
  _meta/config.yaml             org config the harness reads (see Configuration)
  <slug>/
    mission.yaml                THE MAIN RECORD. Committed and pushed on every update.
    README.md                   generated: GitHub view with mermaid journey and graph
    report.html                 generated: the rich report with the Closure tab (overwritten, never a new dated file)
    computed.json               generated: live Jira/GitHub status with fetched_at
    closeout-facts.json         generated by `mission closeout gather` (facts only, UNKNOWN when unread)
    closeout.yaml               the close-out: items, action manifest, approvals by hash, UNKNOWN dispositions
  _closeout/<scope>/            close-out of a scope that has no mission record, plus closeout.html (the standalone page).
                                A mission swept before its record existed keeps its close-out files here; the scripts find them.
    evidence/                   optional supporting files
```

- **GitHub root issue** in the PM repo (`gh_repo` in the mission config, see "Configuration") with the label `kind:mission`. Its body holds the destination and a link to `mission.yaml`. It can be a sub-issue of a component issue. Other issues are **linked** as members, not nested: a GitHub issue can have only one parent.
- Members are links in `mission.yaml`: Jira URLs, GitHub URLs, ticket folders, session folders. GitHub's web view cannot follow a symlink, so a symlink is never the only record.
- Tracker status is never written by hand. `mission_fetch.py` reads it live. Local status claims rot (12 of 13 lagged Jira in the 2026-11-09 audit).

Schema: `references/schema.md`. Which event writes which field: `references/update-procedure.md`. Close-out sweep and `closeout.yaml` shape: `references/closeout-procedure.md`.

## Configuration

The harness holds no org names. Deployment values live outside it:
- `~/.config/mission/config.yaml` (or `$MISSION_CONFIG`): `pm_root: <abs path to the project-management repo>`. `$MISSION_PM_ROOT` overrides it.
- `<pm_root>/missions/_meta/config.yaml` (versioned in the PM repo): `gh_repo` (owner/name of the PM GitHub repo), `jira_browse` (Jira browse URL prefix), `jira_org` (the `--org` value for `jira_skill.py`), optional `jira_key_pattern` and `mr_unknown_reason`.

A missing value is never guessed. The tracker calls that need it report `UNKNOWN`, and `mission new` needs `--no-issue`.

## Running the scripts

One dispatcher runs every script with its dependencies:

```bash
~/.claude/skills/mission/scripts/mission <new|lint|fetch|render|sync|log|closeout|thread|threads> [args]
```

Below, `mission <cmd>` means that full path. Never `cd` in Bash (a zsh override hangs). The scripts use absolute paths.

## Commands

Log every command first: `mission log use --command <cmd> --mission <slug> --session <session-slug>`.

### `/mission start <destination>` (alias `/mission init`): create a mission

1. Search for an existing mission first: read `missions/INDEX.md` and grep the aliases in each `mission.yaml`. If one matches, offer to join it instead.
   Then look for existing work on the same capability: the org bibliothèque (`INDEX.md`, `ALIASES.md`), open GitHub issues (`gh issue list -R <gh_repo> -S "<keywords>"`), and the named tickets' parents and links. Add what you find as members, or record it in `why`. A mission that ignores an existing reader or prior attempt starts stale.
2. Agree with Gabriel on four things: a slug, a title, a destination of 1 or 2 lines ("done looks like…"), and a parent component issue if there is one. Propose them, and do not interrogate.
3. `mission new --slug <slug> --title "<title>" --destination "<…>" --why "<…>" [--parent <N>] --session <session>`. This creates the folder, `mission.yaml`, and the `kind:mission` root issue, then links the parent.
4. Fill in `mission.yaml`: members (the tickets, issues and folders already known), aliases, next milestone, scope constraints, and a first graph. Use the Edit tool.
5. `mission sync <slug> -m "create mission" --session <session> --status-comment`.
6. Tell Gabriel the slug, the root issue link and the record link.

### Threads: capture each one when it opens (a skill duty in every session on a mission)

A thread is one line of work or thought: an intent, a rabbit hole, an open door, a handoff, a nugget, an ask or a finding. Write it the moment it opens, with `mission thread add|set|resolve` (never by hand: the helper takes an flock and rewrites only the `threads:` block). At close, the sweep re-checks this list; it does not rebuild it. The full event map (which event writes which field, including `session:handoff`, `pickup`, `report-back` and the `session:check` reconciliation) is in `references/update-procedure.md`, section "Threads".

The short version:
- An aside starts ("wait, let me check…"): `thread add --kind rabbit_hole`. It converges: `thread resolve --how evidence --link …`.
- Something is noticed and not pursued ("we should also…", "later"): `thread add --kind open_door`.
- A handoff is written: `thread add --kind handoff --home "<prompt>" --child "<intent>"` (one child per intent). The report-back resolves them.
- A needs-you item: the thread gets `--state needs_you` with a question, options and a **recommendation** (the lint warns when it is missing).
- At every `session:check`: reconcile the session's threads (`thread list --session <s>`): DONE resolves with evidence, ABANDONED drops with a named person and a reason, TICKET parks with an accepted home.

A record that predates threads: `mission threads import <slug> --session <s>` once. Imported threads are marked `origin.event: imported`, and the report counts them apart from live captures.

### `/mission` or `/mission <slug>`: resume

Use this at the start of any session that touches the mission.
1. Read `missions/<slug>/mission.yaml`. Its `decisions` (ratified), `disproven` and `scope_constraints` win over any other file, ticket or library page. If another file contradicts them, the other file is stale. Say so, and do not use it.
2. `mission fetch <slug>` for live tracker status. It also compares each thread with its snapshot and marks drift.
3. Give a terminal digest at the current dial level (see "Terminal replies"):
   - the destination;
   - the next milestone;
   - "needs you", with IDs and options;
   - mismatches;
   - open threads and drifted threads (`mission thread list <slug> --state open,needs_you`);
   - the last journey entry.

### `/mission update`: write back

Run it whenever mission truth changes, and always before the session ends.
1. Apply the writes from `references/update-procedure.md` for what happened: decisions, disproven claims, needs-you items, asks, parked tracks, members, artifacts, messages, graph, terms, the matching thread writes, and one `journey` entry per session.
2. Add a `changes` entry for each meaningful change.
3. `mission lint <slug>`. Fix every error.
4. `mission sync <slug> -m "<what changed>" --session <session> --status-comment`. This commits and pushes, and posts a short status comment on the root issue.

An update is done only when the push succeeded. A local commit is not an update.

### `/mission report [<slug>]`: the HTML view

1. `mission fetch <slug>`.
2. `mission render <slug> --open`. This writes `report.html` and opens it in the browser.
3. In the terminal, print the `file://` link and three lines: the verdict, the needs-you count, and the number of changes since the last report.

The report has six views (keys 1 to 6):
- **Mission**: verdict, tiles, needs you, deliverables, asks, messages and artifacts. One tile, "Open threads · closure readiness", links to the Closure tab. The Mission tab does not repeat the closure cards: one queue per purpose.
- **Closure**: every thread, Needs you first (big misses with live risk first, the approval batch, smaller calls; during the mission the open threads lead), then collapsed buckets, "How we searched", "Where each thread lives" and "How these threads were found". One row per thread opens into a card with a Do-now box. Every reference is a link.
- **Journey**: trajectory with gaps, sessions, decisions, disproven claims, parked tracks and trackers.
- **Context graph**.
- **Latest changes**: a sliding window since the last report.
- **Sources**.

A report never creates a new analysis file. If the record is thin, update it first. Mid-conversation "big picture" requests use the same command: update, then report.

### `/mission check [<slug>]`: health and drift audit

Read-only. Use it at any time, not only at the end.
1. `mission fetch <slug>` and `mission closeout gather <slug>`.
2. Report in the terminal: tracker status against the record, orphans, false premises, drafts with no posted record, dangling handoffs, and every `UNKNOWN` source. `UNKNOWN` is never a pass. A draft with no posted record is not unsent until you check its target: it may be published already.
3. Change nothing in Jira, GitHub or the record. Offer `/mission update` for the findings.

### `/mission check --close [<slug>]`: the close-out sweep

Run it when the main feature has shipped. It makes sure nothing small stays undone, and that no big miss hides among the small things. Follow `references/closeout-procedure.md` step by step. In short:
1. `mission closeout gather <slug> [--repo <abs path> ...]`. No mission record? Use `--scope <name> --seed-jira K1,K2 --seed-gh N1,N2 --aliases "a,b" --since <date>`. Besides the tree, it sweeps Jira text, GitHub search and git history since the start, joins Jira/GitHub twins, reads full text to link evidence per AC, and lists security obligations without proof. Every unread or capped source is UNKNOWN.
2. Fan out reviewer subagents: one per twin pair, one per tracker for the rest, one for the sweep hits, one for the security obligations (always). They return buckets. Then `mission closeout coverage <slug>` checks each successor's out-of-scope lines.
3. Apply the 15-step checklist. Write `closeout.yaml` (v2): the bucketed items, the action manifest, and a disposition for each UNKNOWN source.
4. `mission closeout render <slug> --session <s>`. For a mission with a record it merges `closeout.yaml` into the threads (a thread per item; an item with no thread is a capture miss, `origin.event: closeout_sweep`), writes the `closeout` summary into the record, and renders `report.html`: the Closure tab is the close-out report. It writes no `closeout.html`. A scope without a record keeps the standalone `closeout.html`, with a banner that points to `/mission start`. Every Needs-you item carries a recommendation; the lint warns when one is missing.
5. Gabriel answers the decisions and approves a batch by hash: `mission closeout approve`. The script refuses more than 15 closes per batch, and batches that hold a security, cancellation or changed-commitment action.
6. Act on each approved action: re-fetch, act, re-fetch, then `mission closeout record` the read-back. GitHub directly (wayfinder maps through `wayfinder`), Jira and Slack only through `/post-comment`. Never close or transition Jira yourself. A mutation that reported nothing: stop and verify the remote state before any retry.
7. Re-gather, re-render, `mission closeout gate <slug>`, then `mission closeout log <slug>`.

### `/mission close <slug>`

This needs Gabriel.
1. `mission closeout gate <slug>` must exit 0. If it fails, stop and run `/mission check --close`. The gate opens only with an approved manifest whose actions are done with a read-back (or skipped with a reason), a human disposition on every consequential UNKNOWN, a named residual-risk decision on every live risk item, a successor that accepted every ORPHAN and KEEP, and **every thread resolved, dropped, or parked with an accepted home, with no drift**. Resolve T-1 (the big intent) with the link that proves the destination. `mission sync` also refuses `status: done` while the gate is closed.
2. Every member must be done, superseded, or moved to a named successor. Copy the parked `horizon` items into the next mission or a new issue.
3. Set `status: done`, then sync. Close the root issue with a comment that links the record and the report. A phase ending is not a mission ending.

### `/mission feedback "<text>"` and `/mission retro`

Log Gabriel's reactions verbatim. Retro turns repeated complaints into proposed skill changes. See `references/self-improvement.md`.

## Terminal replies while a mission is active

Read `references/terminal-replies.md` once per session. In short:
- Assume Gabriel has not read anything above your current reply, and that he knows only what he confirmed.
- Answer first.
- Never write "see above".
- Never use a bare ID or reference.
- Define new terms once.
- Persist every question before you ask it.
- Follow the detail dial: default 3, "left" means more detail, "right" means less, "refs" means links only.

## Rules that protect the record

- **Authority.** A decision is ratified only with `ratified_by` that links to where a human said it. An agent never ratifies its own proposal. "Do not re-litigate" is valid only on a ratified decision (the lint enforces it).
- **Supersede, do not annotate.** A changed decision gets a new entry with `supersedes`. A disproven claim gets an entry with a grep signature, and you sweep the stale copies. Dead text in other files is deleted or fenced, not annotated.
- **One record.** Never write a second "current status" or "start here" file for a mission. Other files link to `mission.yaml`.
- **Commit explicit paths only.** `mission_sync.py` already does this. The PM repo is single-trunk `main`: never branch, never rewrite history.

## Horizon (not in v1)

- Session meshing: sessions on one mission talking to each other directly. Research tracked in the PM repo.
- A hook that captures Gabriel's asks at turn time. A session-close gate that requires a mission update.
- **Proposal: an open-door capture hook.** Today open-door capture is a skill duty (above). The proposal is a `UserPromptSubmit` and `Stop` hook that matches "we should also", "later", "park that", "not now" and unanswered questions, and writes `mission thread add --kind open_door --event open_door_hook` for the active mission. It catches more, and it is noisier. Decide after 3 missions: if the close-out logs more than 20% of threads as capture misses, build it. Decision 2026-11-13 (default, Gabriel may override): a skill duty now, no hook.
- Integration with the org context graph (`context-graph-sync`).
- Cross-component missions with more than one parent.

## Evals

- `evals/run_layer_a.py` (`uv run --quiet --with pyyaml python3 ~/.claude/skills/mission/evals/run_layer_a.py`): deterministic checks on the lint, render, fetch and close-out (gather UNKNOWN handling, gate, sync refusal), using fixtures. It also checks the close control (approval bound to a manifest hash, read-backs, the 15-close cap, per-item approval classes, UNKNOWN dispositions, named risk decisions, accepted successors), the decision-first report, the big-miss predicates, the close-out log and the check review, the discovery stage (sweep outside the tree with caps and exclusions, twin join, evidence per AC with a text budget, security obligations, successor coverage, pagination, depth exhaustion, recursive UNKNOWN aggregation, record internals), and that no private term appears anywhere in the skill tree. The thread checks cover the threads lint (and that a record without threads still passes), the import (merging, idempotence, origin imported), the live-capture commands (handoff children, resolve and drop proof, the flock under parallel writers), drift at fetch, the thread close gate, and the Closure tab: Needs you first, one full card per thread, the Do-now box, the batch and per-item approval commands, and a render of fixtures that fails on any bare `#N`, `KEY-N` or `!N` outside a link. `evals/report_smoke.js` runs the report JavaScript in node with a DOM stub (node is required: a missing node is a failure, not a pass). It runs the gatherer checks from a real close-out (failed child query, unresolved comment-after-close, drafts with no posted record, ordering without a `blockedBy` edge, reflection moved off its map, untraced map closes) and calibrates the close-out grader in both directions. Run it after any change to this skill. It is registered in `~/.claude-shared-config/evals/manifest.yaml`.
- `evals/evals.json`: behavioral cases for skill-creator. Cases 5 to 8 replay an anonymized real close-out (`evals/fixtures/closeout-scenario/<case>/`): the full scenario, the traps alone, a clean scope that must not invent work, and scope isolation.
- `evals/grade_closeout.py`: scores an agent's close-out answer against `evals/expected/closeout/<case>.json`. Per-item accuracy, plus hard fails for a wrong trap item, a missed ORPHAN, an out-of-scope item, an unreported UNKNOWN source, or any Jira or Slack write. Never copy `evals/expected/` into a sandbox.
